Protocol

The technical specification underlying EvidenceProtocol™.

Disclosed across filed applications: PAT-001 (U.S. provisional #63/960,933), PAT-004 (LocalChain), PAT-005 (attestation ingest), PAT-010 (short-code verification). This page states claims with their assumptions and an explicit account of what the protocol does not protect against.

1. Overview

ZKNOT produces an attestation that a physical actuation occurred on a specific device after an unpredictable challenge was presented, signed by an ECDSA P-256 key held in that device's hardware secure element, and appended to a tamper-evident local log (the ZKNOT LocalChain).

Three separated concerns:

  • Possession of a non-extractable key (device binding), via the secure element — plus, on the PowerVerify line, an optical physically unclonable feature captured by camera and matched against an enrolled baseline.
  • Freshness, via binding each attestation to a single-use, verifier-issued challenge hash.
  • Temporal ordering ("post-nonce"): a finite-state machine prevents the device from assembling an attestation until after the challenge has been displayed and a physical actuation registered, in that order.

The human actuation contributes ordering, not entropy — it is not mixed into the signed material as a secret.

3. Adversary model

Assumed capabilities: observe and record any number of completed attestations and challenges; replay at will; run arbitrary software on a general-purpose host in the display path; attempt pre-computation ahead of challenge issuance; (PowerVerify) present forged or replayed optical material to a verifier's camera.

Out of scope (not defended — see §6): SE key extraction within budget; real-time relay; compromised provisioning.

4. The protocol

The firmware is a finite-state machine. The signable state (S_SIGN) is reachable only along:

S_IDLE
  → (receive challenge, derive challenge_hash) → S_LOADED
  → (display challenge on trusted path)        → S_DISPLAYED
  → (register physical actuation)              → S_ACTUATED
  → (SE signs challenge_hash)                  → S_SIGN  → emit artifact

No edge into S_SIGN bypasses S_DISPLAYED → S_ACTUATED. The artifact carries an ECDSA P-256 signature over the SHA-256 challenge hash, the device public key, and actuation evidence. The verifier accepts iff (1) the P-256 signature verifies against the registered public key over challenge_hash; (2) the challenge was issued here, is unexpired and unconsumed; (3) (PowerVerify) the captured optical feature matches the enrolled baseline within tolerance. On acceptance the challenge is consumed and the artifact appended to the LocalChain, which can later be walked and re-verified (POST /v1/chain/verify).

5. Security properties

P1 — Device binding. A valid attestation demonstrates possession of the SE's P-256 key at signing time. Assumes: the key is non-extractable/uncloned under the assumed budget, and provisioning bound it to the claimed identity.
P2 — Freshness / anti-replay. Each attestation binds a single-use challenge; a replay references a consumed or expired challenge and is rejected. Assumes: the challenge is high-entropy and the verifier enforces single-use and a bounded window (§6.7).
P3 — Temporal ordering ("post-nonce"). Because S_SIGN follows challenge display and actuation, a well-behaved device cannot sign a challenge before it existed. Scope: enforced by the device; only as trustworthy as firmware/SE integrity. The verifier learns "a device whose firmware enforces this ordering signed a fresh challenge," not "a human acted after the challenge."
P4 — Pre-computation resistance. From P2 + P3: the signable state is gated behind an unpredictable challenge, so attestations cannot be made in advance.
P5 — Physical-clone resistance (PowerVerify, optical PUF). Identity is additionally rooted in a photographed physical feature compared against an enrolled baseline within a tolerance threshold. Assumes: the feature is hard to reproduce, capture geometry is controlled, and the matcher's false-accept rate is low enough for the use case. This is a physical-fingerprint-vs-baseline scheme, not a challenge-response PUF; it is subject to §6.5.

6. What this does NOT protect against

6.1 — No proof of who actuated; no biometric liveness. It attests that a physical actuation occurred after display; it does not identify the actuator or distinguish a human from a mechanical actuator. "Human presence" is a deployment assumption.
6.2 — No defense against real-time relay (mafia-fraud / MITM). Relaying a displayed challenge to a genuine remote device and the attestation back, inside the window, can be accepted. There is no distance bounding.
6.3 — Display-path dependency (WYSIWYS). The guarantee that the actuator responded to the challenge that was actually signed holds only if shown == signed. Strong with a device-owned display; weaker when a compromised host renders the challenge.
6.4 — SE physical-security envelope. Decapsulation, fault injection, and side-channel key extraction are out of scope.
6.5 — Optical-PUF presentation / spoofing. Because the PowerVerify feature is verified by photo against a baseline, an adversary may present a printout, screen, or replica, or exploit the matcher's false-accept tolerance. There is no inherent capture-liveness guarantee. Treat the baseline as sensitive: if it leaks, it defines the forgery target.
6.6 — Honest provisioning assumed. Compromise of enrollment (key or optical baseline) defeats the guarantees.
6.7 — Verifier-side enforcement required. P2 holds only if the verifier treats challenges as single-use and expires them.
6.8 — Not a secure channel / not key agreement. No payload confidentiality is provided.

7. The ZKNOT LocalChain

Accepted artifacts are appended to a local, hash-linked log: each record commits to its predecessor, so reordering, deletion, or silent modification of prior records is detectable by walking the chain. This provides tamper-evidence and append-only ordering — not confidentiality, and not a proof of any hidden statement. ("ZK" denotes ZKNOT; this is not a zero-knowledge proof system.)

8. Assumptions (consolidated)

  1. SE P-256 key non-extractable/uncloned under the assumed budget.
  2. Challenges high-entropy, single-use, freshness-windowed by the verifier.
  3. Firmware FSM correctly enforces ordering.
  4. Display-path integrity to the degree the deployment requires (§6.3).
  5. (PowerVerify) controlled capture geometry; low matcher false-accept rate; baseline kept secret.
  6. Honest provisioning/enrollment.

9. Verification

Verification splits into checks any relying party can perform offline and checks that require the issuer (or the published chain).

Client-side, with only a SHA-256 implementation and an ECDSA P-256 verifier, a party can independently confirm:

  • the artifact's signature verifies against the claimed device public key over the SHA-256 challenge hash (P1, device binding);
  • the client-authoritative short code (PAT-010 §3, XXXX-XXXX-XXXX) recomputes from the artifact, so the human-readable code is not server-assigned trust.

No proprietary library is required, and a verifier need not trust ZKNOT's servers to confirm that a specific device key signed a specific challenge hash.

Server-mediated (or via the published chain):

  • challenge freshness and single-use (P2) depend on the issuer's challenge ledger; an offline client cannot by itself know a challenge was unconsumed;
  • chain position and tamper-evidence are confirmed by walking the LocalChain (POST /v1/chain/verify), verifiable by any party holding the chain.

Net: signature and short code are independently checkable offline; freshness is the single property that requires the issuer or an out-of-band freshness signal.

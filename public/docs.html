Concepts

Attestation
A signed record that a physical actuation occurred on a specific device after a challenge was presented.
Challenge hash
The SHA-256 hash of an unpredictable, single-use challenge issued by the verifier; the value the device signs.
Secure element (SE)
Hardware holding the device's non-extractable ECDSA P-256 key.
Optical PUF
(PowerVerify only) A photographed physical feature matched against an enrolled baseline; not a challenge-response PUF.
FSM-gating / post-nonce ordering
The device firmware only reaches its signing state after the challenge is displayed and an actuation registered — the human action proves ordering, not entropy.
LocalChain
A hash-linked, tamper-evident, append-only log of accepted attestations. "ZK" denotes ZKNOT, not zero-knowledge.
Short code
A human-readable identifier for an attestation (PAT-010). Two forms: client-authoritative XXXX-XXXX-XXXX and server-derived ZK-XXX-XXXX.

Quickstart

  1. The device signs the SHA-256 challenge hash with its SE key.
  2. Submit the signed artifact: POST https://api.zknot.io/v1/attest → returns a chain entry and a short code.
  3. Anyone resolves that code with no login: GET https://api.zknot.io/v1/verify/{code}, or via the UI at verifyknot.io.

Verification

Verification splits into checks any relying party can perform offline and checks that require the issuer (or the published chain).

Offline (SHA-256 + ECDSA P-256 only)

  1. Parse the artifact: device public key, challenge hash, signature, and (if present) the client-authoritative short code.
  2. Verify the ECDSA P-256 signature against the device public key over the SHA-256 challenge hash. A pass establishes device binding (Protocol P1).
  3. Recompute the client-authoritative short code from the artifact (PAT-010 §3) and confirm it matches the code presented to you — so the human-readable code is not server-assigned trust.

No proprietary library is required, and you need not trust ZKNOT's servers to confirm that a specific device key signed a specific challenge hash.

Server-mediated (or via the published chain)

  • Freshness / single-use (Protocol P2) depends on the issuer's challenge ledger — an offline client cannot, by itself, know a challenge was unconsumed. This is the one property that requires the issuer or an out-of-band freshness signal.
  • Chain position and tamper-evidence are confirmed by walking the LocalChain: POST /v1/chain/verify returns the first failing position, if any. Any party holding the chain can run this.

Artifact & short codes

An attestation artifact carries, at minimum, the device public key, the SHA-256 challenge hash, the ECDSA P-256 signature over that hash, actuation evidence, and a short code. The cryptographic primitives are SHA-256 (hashing) and ECDSA over NIST P-256 (signing) — both available in every major language, which is what makes offline verification possible.

Short codes follow PAT-010 §3 in two forms: XXXX-XXXX-XXXX is client-authoritative — derivable from the artifact without the server — and ZK-XXX-XXXX is server-derived. The verify endpoint accepts either, plus the raw artifact UUID.

FAQ

Does an attestation prove a specific human acted?
No. It attests that a physical actuation occurred after the challenge was displayed. It does not identify the actuator or distinguish a human from a mechanical one.
Is it resistant to real-time relay?
Not on its own — there is no distance bounding. See Protocol §6.2.
Is the LocalChain zero-knowledge?
No. "ZK" denotes ZKNOT. It is a hash-linked, tamper-evident, append-only log verified with SHA-256 and ECDSA P-256.
Do I need a ZKNOT library to verify?
No. Offline verification of the device signature needs only a SHA-256 implementation and an ECDSA P-256 verifier.
